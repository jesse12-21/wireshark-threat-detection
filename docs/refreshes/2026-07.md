# Detection Refresh — July 2026

**Refresh ID:** 2026-07 · **Reviewed:** 2026-07-29 · **Previous baseline:** 2026-05-29 · **Next review:** 2026-10-29

*Part of the [refresh log](README.md).*

Detections expire. Not because they were written badly, but because the protocols they observe keep moving. A rule that was sound in May can be quietly wrong by July, and the failure mode is silent: it keeps firing, the alerts keep looking plausible, and nobody notices the signal has drained out of them.

This document records a scheduled review of every detection in this repository against the state of the protocols as of July 2026. One rule was deprecated outright, three were added, and one existing capability turned out to matter considerably more than it did at the time it was written.

## 1. Encrypted Client Hello broke a rule in this repository

### What the original rule assumed

`tls_no_sni_external.yml` detected TLS Client Hello messages sent to external addresses with no Server Name Indication. The logic was straightforward and, in 2024, correct: browsers, updaters, and package managers all send SNI because virtual-hosted infrastructure requires it. A client that omits it is probably connecting to a hardcoded IP, which is what implants with embedded C2 addresses do.

### What changed

Encrypted Client Hello splits the handshake into a visible `ClientHelloOuter` carrying a generic cover name, and an encrypted `ClientHelloInner` carrying the real destination. The plaintext SNI — the single most-used signal in TLS monitoring — stops being available for the traffic that adopts it.

Adoption is not hypothetical. Cloudflare enabled ECH by default across its customer base in late 2023, and Firefox and Chrome shipped support that October. The specification is at draft 25 and not yet formally ratified, but implementation is mature and widespread. Because the overwhelming majority of top sites sit behind a handful of CDNs, ECH availability propagated across a very large fraction of the web through a small number of provider decisions.

Two second-order effects matter more than the headline:

**GREASE ECH removes the obvious workaround.** The natural response to "SNI is disappearing" is to detect ECH usage instead. That does not work. Browsers emit an ECH-shaped extension on effectively every Client Hello whether or not ECH is actually in use, precisely so that privacy-preserving connections cannot be singled out and blocked. The lesson from ESNI — its predecessor, which was trivially identifiable and therefore trivially blockable — was learned deliberately. Extension presence carries no information.

**Adversaries are already there.** NTT Security Holdings identified malware using ECH for command-and-control while analysing targeted attacks against Japanese organisations. This is the ordinary pattern: any mechanism that reliably conceals a destination gets adopted by people who want their destination concealed.

### Why the rule had to go rather than be tuned

The failure is bidirectional, which is what makes tuning insufficient:

- **False positives rise.** Legitimate ECH traffic increasingly trips a rule designed to catch malware. The alert volume grows while the precision falls.
- **False negatives rise at the same time.** An adversary using ECH is now inside the same bucket as every privacy-preserving browser session. The rule stops distinguishing.

A detection that gets noisier and blinder simultaneously has no threshold that fixes it. It gets deprecated, with the reasoning recorded and a successor named.

### What replaced it

`tls_ech_without_dns_config.yml` keys on a precondition the protocol cannot avoid.

A conforming ECH client cannot encrypt its `ClientHelloInner` without the server's `ECHConfig`. That config is published in the target's HTTPS resource record (DNS type 65, RFC 9460). The lookup is mandatory, and it happens in the clear on networks using conventional DNS.

So: an ECH session with no preceding HTTPS-RR query from the same host means the client already had the config — hardcoded, or delivered out of band. No mainstream browser does this. An implant with an embedded `ECHConfig` does exactly this.

The honest limitations, which are stated in the rule and in `ech_analyze.sh` rather than discovered by whoever deploys it:

- DNS caching can place the lookup outside the correlation window
- DoH and DoQ hide the query entirely, requiring resolver logs instead of passive capture
- Session resumption can reuse a config obtained earlier

It is a lead-generator, not a verdict. That is the correct claim to make for it.

## 2. Post-quantum adoption created a detection that improves over time

Most TLS detections decay. This one does the opposite, which is unusual enough to be worth building.

Hybrid post-quantum key agreement moved from experiment to default across mainstream browsers and the major CDNs during 2025 and 2026. Roughly half of measured public domains now negotiate it, driven by ML-KEM-768 standardisation under FIPS 203. The group those clients present is `X25519MLKEM768`, IANA code point 4588 (`0x11EC`); browsers send it alongside a classical `X25519` share by default.

The detection inverts the usual framing. Rather than asking *what does this client have that malware has*, it asks *what does every current browser have that malware does not*.

Malware TLS stacks lag. Implants built on statically linked older OpenSSL, on bespoke TLS implementations, or on runtimes pinned to pre-3.5 OpenSSL cannot offer PQ groups — OpenSSL only shipped ML-KEM as a built-in provider in 3.5, released April 2025. An implant that spoofs a browser JA4 to blend into normal traffic will still fail to present a post-quantum key share, because the fingerprint is cosmetic and the cryptographic capability is not.

`tls_missing_pq_keyshare.yml` looks for that mismatch: a browser-shaped JA4 with no PQ group offered.

As PQ adoption climbs, the population of legitimate classical-only browsers shrinks, and the signal sharpens. The largest false-positive source is not malware-adjacent at all — it is enterprise TLS-inspection proxies rewriting the Client Hello and stripping groups. Those get excluded by egress IP.

## 3. AI traffic is a network surface that did not exist when this project was scoped

Two additions here, both covering ground that conventional network monitoring was not designed for.

### LLM inference APIs

The prompt field is an egress channel with no inspection on it. A user pasting a customer table into a chat window, or an implant submitting a credential store, produces an ordinary HTTPS POST to a reputable domain. Domain reputation is clean. Certificate validation passes. Conventional DLP sees nothing distinguishable.

Without content inspection, request-direction byte volume is the strongest available signal. Interactive chat produces tens of kilobytes per session; bulk document submission produces orders of magnitude more.

The complication, stated up front: agentic coding assistants legitimately submit large repository context, and they are now routine developer tooling. This detection generates real false positives on developer subnets and needs baselining rather than a fixed threshold. It is included anyway, because "shadow AI inventory" is a question most organisations currently cannot answer at all.

### MCP servers

Model Context Protocol connects assistants to external tools. Connecting to an untrusted MCP server grants that server influence over what the assistant does with everything it can reach — which is why vendors shipped pre-installation scanners for prompt injection and malicious tool definitions during 2025 and 2026.

Those scanners operate at the endpoint and supply-chain layer. *Which MCP servers do hosts on this network actually reach* is a different question, and it is a network question. `mcp_server_connection.yml` covers the Streamable HTTP transport. The stdio transport is local-only and generates no network artifacts, so this rule cannot see it — an explicit coverage gap, not an oversight.

### A false-positive interaction worth knowing about

Agentic tool-use traffic is periodic. It will resemble C2 beaconing to `beacon_detect.sh` and to `https_beacon_pattern.yml`.

The discriminator is payload-size variance. Beacons are uniform by design — small, consistent check-ins. Agent traffic is bursty and irregular, because tool calls carry different amounts of data. Before treating a periodic connection to an AI endpoint as C2, check the size distribution. This is documented in the playbook so it does not have to be rediscovered at 2am.

## 4. What ECH did *not* break

The most useful conclusion from this review is about what survived.

ECH removes plaintext destination metadata. It does not touch:

- **Connection timing.** Beacon interval, jitter, and periodicity are fully intact. `beacon_detect.sh` works exactly as well after ECH as before.
- **Payload size distribution.** Uniformity of transferred bytes is unaffected.
- **JA4 fingerprinting.** JA4 is computed from the outer Client Hello, which remains visible.
- **Destination IP and ASN.** The address is still on the wire.
- **DNS-layer metadata**, on networks not using encrypted DNS.

There is a strategic point here. As content-level visibility erodes — ECH, TLS 1.3 encrypted certificates, DoH — **behavioural and statistical detection becomes proportionally more valuable**, because it operates on properties that encryption does not conceal. The statistical beaconing work in this repository was written before that shift was obvious. It is more relevant now than when it was built, not less.

The general lesson: detections that key on *what is in the traffic* have a shelf life set by the encryption roadmap. Detections that key on *how the traffic behaves* age considerably better.

## 5. Detection lifecycle policy

This review established a working practice for the repository.

**Rules are deprecated, not deleted.** A removed rule loses its history. A deprecated one keeps the record: what it assumed, what changed, what replaced it. `tls_no_sni_external.yml` retains `status: deprecated`, a dated explanation, and the successor's UUID.

**Every rule states its expiry conditions.** If a detection depends on a protocol assumption, that assumption is written down where the next person will find it.

**Limitations are declared, not discovered.** DNS caching, DoH blind spots, stdio transport invisibility, proxy interference — these are in the rule files and the script headers. A detection whose failure modes are documented can be deployed with appropriate confidence. One whose failure modes are unknown cannot.

**Rules are validated in CI.** `.github/workflows/validate-detections.yml` runs YAML validation, `sigma check`, UUID uniqueness, backend conversion smoke tests, ShellCheck, and a placeholder scan on every push touching `detections/` or `scripts/`. Detection-as-code means the same discipline software gets.

**Reviews are scheduled, not incidental.** Next review: **2026-10-29** — see the [refresh log](README.md) for early-trigger conditions. Sooner if ECH ratifies, PQ adoption crosses meaningful thresholds, or MCP transport patterns shift.
